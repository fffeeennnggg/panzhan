# 盘栈夸克直链下载策略实测（2026-10-19）

结论：**HTTP/1.1、8 路并发、10 MiB 分块是本轮最值得保留的候选配置，但尚不能确认它能持续提速。** 第一组交错顺序的长窗口复测中，其中位数为 11.22 MiB/s，默认配置为 10.84 MiB/s，差约 3.5%；随后反向顺序检查时，两种配置均出现明显低速。因此，不能把这 3.5% 当作确定收益，更没有测出解除网盘限速或数倍加速。

本机物理网卡“以太网 2”（接口 8）当前协商速率是 **100 Mbps**，理论上限 11.92 MiB/s，多数组合已经接近本机约 11.2 MiB/s 的实际上限。这个环境无法判断千兆网络下哪种方式上限更高。未逐窗口采集网卡总流量，无法进一步区分这些下降来自 CDN、其他流量还是本机负载。

## 测试接入和方法

- 使用盘栈实际的 `internal/download.Engine.Fetch`，不是独立编写一个 HTTP 下载器。运行环境为本机 Windows、Go 1.26.4、Python 3.14；没有部署到 NAS。
- 同一账号、同一个 2,607,095,503 字节云端文件，CDN 为 `dl-pc-zb.drive.quark.cn`。每个测试进程获取一次下载链接，组内复用；每轮重建 HTTP transport 和独立临时目录，不复用连接或部分下载文件。
- 16 个初筛窗口：预热 1 秒、计量 6 秒。9 个交错复测及 4 个反向复测窗口：预热 2 秒、计量 12 秒。
- Python 进程通过 `time.monotonic()` 计时，统计响应体实际读取字节；不使用客户端显示速度或被 OpenSpeedy 修改的时钟。这次矩阵未启用 OpenSpeedy。
- 每轮应用层读取上限 192 MiB，结束后取消并清理。总计 29 个有效窗口，应用层累计读取 2,882,012,380 字节；这是部分下载吞吐测试，未做完整文件完成时间和哈希校验。应用层上限不代表网卡流量上限，协议开销和内核预读未计入。
- 有效窗口均收到 HTTP 206，没有提前结束或下载错误。长窗口复测增加重复 Range 计数，全部为 0；初筛版本未记录此计数。采样 IPC 往返均小于 0.1 秒。
- 通过 `httptrace.GotConn` 验证真实连接数：HTTP/1.1 的 3/8/16/32/64 路分别建立对应数量的连接；自动模式实际为 HTTP/2，3/8/32 路分别是在 1 条 TCP 连接上的多个响应流。没有把 HTTP/2 流数误认为 TCP 连接数。
- 生产引擎并发上限仍是 8；16/32/64 路仅通过 Go build overlay 在实验程序中放宽。最终校验确认生产下载源码与测试前哈希一致。现有账号文件逐组校验未变，临时下载目录已清理，测速进程已退出。

## 4 轮反向顺序检查

为检查时间顺序和网络波动，再测 B / A / A / B，参数和计量窗口同上。

| 顺序 | 配置 | 速度 MiB/s |
|---:|---|---:|
| 1 | H1 8 路 | 4.950 |
| 2 | 默认 3 路 | 3.217 |
| 3 | 默认 3 路 | 5.125 |
| 4 | H1 8 路 | 11.238 |

H1 同样会下降，不能只选前一组接近 11.2 的三个结果说它稳定。此组网络条件变化很大，不与前面直接混成一个“提升百分比”。它也说明默认在某个低速窗口与候选在另一个高速窗口的巨大倍数差，不能直接归因于配置。

## 测试工具修正与验证

首次诊断中，默认样本正常，但强制 H1 的样本没有有效响应。原因是克隆已初始化的 Go transport 时保留了 H2 ALPN，仅指定 H1 协议没有清除它，导致用 H1 解析器读到 H2 帧。修正只涉及实验工具：明确重置 ALPN 和协议映射，并增加本地 H2 TLS 服务的回归测试。该回归用例修正前失败、修正后通过。

这次失败的 H1 样本及相邻默认样本不纳入 29 轮比较，原始诊断仍保存在结果 JSON，未当作“不提速”的证据。

最终验证通过：

```text
go test ./internal/download ./internal/quark ./cmd/panzhan-speedprobe -count=1
go vet ./cmd/panzhan-speedprobe
python -m py_compile scripts/test_download_matrix.py
```

## 教程建议与适用范围

- [AList 历史讨论 #4175](https://github.com/AlistGo/alist/issues/4175)：小 Range 分块是本次测试分块大小的来源之一。盘栈原本已经采用 10 MiB 分块，不能把这当作一个尚未启用的全新加速手段。
- [Gopeed 夸克扩展](https://github.com/iGwkang/gopeed-extension-quark)：高并发建议是本次 16/32/64 路初筛的动机；教程推荐并不等于实测最优。本次未运行外部 Gopeed 或 aria2，也未测 256 路。
- [Linux.do 直链下载讨论](https://linux.do/t/topic/167134)：外部下载器体验是可供验证的线索，不能直接替代盘栈同链路对照结果。
- [LinkSwift #405](https://github.com/hmjz100/LinkSwift/issues/405)：下载链路请求中的新 Cookie 可能影响链接有效性；本次所有有效窗口均为 206，没有凭证失效证据，也没有证明通过 Cookie 能解除速度限制。

本轮支持保留 H1 8 路作为后续候选，不支持现在把并发硬提到 64 或承诺下载速度翻倍。要判断千兆网络或 NAS 上的收益，需要在对应环境重复对照；本次没有修改正式下载配置。

完整逐轮数据、诊断样本、源码哈希与验证状态见 [结果 JSON](2026-10-19-download-strategy-results.json)。
