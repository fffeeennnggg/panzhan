# 飞牛网盘资源应用：源码能力提取调研

调研日期：2026-10-15。目标架构：x86_64。阶段：源码调研，不进行产品实现。

## 1. 需求的准确理解

开发一个全新的飞牛 FPK 应用，拥有自己的界面、搜索、账号、转存、下载和任务系统。参考四个项目的源码，按模块提取或改造所需能力，使这些能力直接成为新程序的一部分。

不内置 AList/PanSou/QAS 整套应用，不启动它们的后台服务，不把对它们 API 的调用当成“功能提取”。对于来自不同语言的能力，可在遵守原许可的前提下移植到统一语言，移植后的代码仍需保留来源和许可。

用户已经确认：第一版先打通夸克“搜索 → 选择资源 → 自动转存 → 下载到 NAS 指定目录”。搜索覆盖面以后通过搜索源扩展，其他网盘的转存下载以后通过网盘适配器扩展。

## 3. 总体结论

这个方向在代码结构上可行，推荐形成统一 Go 核心，把四个项目中适用的算法、协议处理和解析逻辑改造成新程序自己的模块。

其中 AList 最有价值的是夸克原文件直链处理和分片下载；QAS 最有价值的是分享解析、转存及结果 FID 处理；PanSou 最有价值的是搜索源适配、链接/提取码解析与聚合。PanHub 当前仓库主要提供前端交互，无法从中取得未公开在该仓库中的搜索、转存后端。

目标运行形态：一个本程序的后端进程，内嵌前端静态资源，配合自己的任务数据库与下载临时文件。FPK 负责安装、入口、目录授权和生命周期。该形态不需要用户先安装 AList、PanSou、QAS 或 Docker；普通的 HTTP、HTML 解析、SQLite 等库仍是正常源码依赖。

## 5. AList：到底需要提取什么

### 5.1 源码中的实际链路

跨存储复制在 `internal/fs/copy.go` 中获取源文件链接，构造可读数据流，再写入目标存储。对于“夸克 → NAS 本地目录”，它本质上是 NAS 从夸克下载真实字节，不是网盘与 NAS 之间的云端秒传。

关键证据：

- [`getDownloadLink`](https://github.com/AlistGo/alist/blob/ea628f9a4fb2dcd1f400a4a3f91ccb59b3c1da69/drivers/quark_uc/util.go#L180) 调用原文件 `/file/download` 接口，组合下载地址和请求头。
- 同一文件 `applyLinkLimit` 将驱动的并发数与分片大小传入下载链路；该版本夸克驱动默认配置为 3 路并发、10 MiB 分片。通用下载器另有自己的默认值，不能把二者混淆。
- [`GetRangeReadCloserFromLink`](https://github.com/AlistGo/alist/blob/ea628f9a4fb2dcd1f400a4a3f91ccb59b3c1da69/internal/stream/util.go#L17) 根据链接中的分片参数使用并发下载器。
- [`Downloader.Download`](https://github.com/AlistGo/alist/blob/ea628f9a4fb2dcd1f400a4a3f91ccb59b3c1da69/internal/net/request.go#L68) 及其分片处理逻辑负责 Range、并发控制、流式输出及一定范围内的重试。

### 5.2 对速度判断有用的细节

1. 下载请求携带 Cookie、Referer、User-Agent；取直链时的会话与下载时必须匹配。该版本专门使用 Cookie 快照避免并发刷新导致签名不一致。
2. 有原文件直链和转码播放地址两条路径。下载原始文件必须走原文件分支。
3. 分片并发可能提高吞吐，但也可能遇到限流，不能认为并发越大越快。
4. 上游会话刷新与临时直链是两个状态；账号可访问目录不代表之前获取的直链一直有效。

因此应提取的是“直链 + 正确会话与请求头 + Range 下载”能力。用户实际使用的 AList 版本、驱动类型、账号和网络尚未核实，不能断言其高速完全由本次阅读版本的某一处实现造成。

### 5.3 不宜直接复制的部分

`drivers/quark_uc` 引用了 AList 的 `internal/model`、`internal/driver`、`internal/op` 等，且包含上传、删除等不需要的功能。Go 的 internal 可见性与框架类型耦合意味着它不是一个可直接用于外部新项目的小型独立 SDK。

新程序应保留需要的协议与下载逻辑，换成自己的文件、账号、直链和任务类型。不要为了复用一个驱动，把 AList 的全部存储框架、WebDAV、S3、虚拟挂载和管理后台一并引入。

本地 `Local.Put` 采用直接创建目标文件再拷贝数据。该逻辑不能直接满足“保留断点、避免误覆盖、校验完成后才显示正式文件”的要求。新程序需要独立的临时文件与落盘完成协议。

## 6. QAS：提取夸克分享与转存协议

核心参考文件是 [`quark_auto_save.py`](https://github.com/Cp0204/quark-auto-save/blob/1c35e969332e03980f60c34fc15b2467370bafb2/quark_auto_save.py)，不需要带入它的 WebUI、定时脚本入口、通知或媒体库插件。

应保留的协议步骤：

1. 解析分享 ID、提取码、分享子目录。
2. 取得分享访问令牌，分页读取分享内容。
3. 获取或创建用户网盘中的任务目标目录。
4. 提交所选文件的分享 FID 与分享文件令牌，保存返回的转存任务 ID。
5. 查询转存结果，取得转存后的 FID，并核实目录与文件清单。

源码在批量转存时采用每批 100 项，并注释返回的 `save_as_top_fids` 数量限制。新程序可沿用该批处理策略，仍需实测对应接口版本。转存后的 FID 与分享侧 FID 不应假定相同；源码显式保存这层对应关系。

需要重新设计的地方：网络超时与轮询截止时间、转存意图与结果的持久化、结果不明确时的核对策略、取消和重试边界。`query_task` 的当前循环逻辑不能原样作为可重启应用的任务引擎。

建议将这些必要能力移植为原生 Go 夸克客户端，而不是继续运行整个 Python 项目。AList 与 QAS 参考实现使用的 API 主机、会话和响应处理有差异，移植时需统一验证，不能机械拼接函数。

额外观察：QAS 的 `do_save_check` 会转存测试文件后删除并清理回收记录；它不适合作为新应用默认的“连接测试”。连接测试应优先采用只读接口，需要写入的测试应使用明确的独立测试任务。

## 7. PanSou：提取搜索源，不依赖 PanSou 服务

可直接研究的代码有：

- [`plugin/plugin.go`](https://github.com/fish2018/pansou/blob/221665fb2c9279f22af4684ea2d8c0c331eac1cc/plugin/plugin.go)：来源接口、注册、异步搜索基类。
- [`plugin/`](https://github.com/fish2018/pansou/tree/221665fb2c9279f22af4684ea2d8c0c331eac1cc/plugin)：各来源的请求、页面解析与详情提取。
- [`util/parser_util.go`](https://github.com/fish2018/pansou/blob/221665fb2c9279f22af4684ea2d8c0c331eac1cc/util/parser_util.go)：网盘链接、提取码与消息解析。
- [`service/search_service.go`](https://github.com/fish2018/pansou/blob/221665fb2c9279f22af4684ea2d8c0c331eac1cc/service/search_service.go)：多来源调度、合并、排序与 TG 搜索。

适合的提取方式是先选少量来源，将“请求构造 → 搜索结果解析 → 必要时进入详情页 → 输出标准资源”移入自己的 SearchSource 接口。之后按来源维护，避免把 PanSou 的 HTTP 服务、认证、全部插件和缓存全局状态一起移入。

检查的代表来源包括 `labi`、`zhizhen`、`muou`。它们包含站点模板、域名候选、解析选择器、详情页请求和各自超时设置；部分来源共享相似模板，但不同站点仍需分别验证。源码存在适配器不代表该来源今天可用，第一批来源必须通过本地网络实测后再确定。

TG 搜索应作为可选来源：其可达性与普通网站不同，失败不能阻塞其他来源或被缓存为“确定无资源”。搜索状态需要区分无结果、超时、需要认证与解析失败。

资源去重应以网盘类型与规范化分享 ID 为主，保留原来源、更新时间和提取码；不同链接即使标题相同也可能是不同版本，不能全部合并成一个文件。搜索结果只能提供候选信息，失效与可转存性最终需由夸克适配器核实。

“多网盘搜索”与“多网盘自动下载”是两种独立能力。百度结果不能因为程序接入了夸克账号，就自动转存进夸克。未来每种网盘都需要自己的账号与转存/下载适配器。

## 8. PanHub：有价值的交互参考与仓库缺口

源码 [`src/config.ts`](https://github.com/wu529778790/panhub.shenzjd.com/blob/e1cd79df2ceecab99d63a6ad35f218eb4b8a4615/src/config.ts) 直接配置其公网 API 与 wx-auth 地址；[`useTransfer.ts`](https://github.com/wu529778790/panhub.shenzjd.com/blob/e1cd79df2ceecab99d63a6ad35f218eb4b8a4615/src/composables/useTransfer.ts) 调用服务端转存接口，并未实现网盘转存协议。

可参考的交互是流式返回搜索结果、按网盘分组、追加结果去重、搜索取消/继续以及明确的失效状态。但应在新应用中自行实现对应的前后端流程。

本仓库的“获取成功”主要面向返回可用分享链接或口令，并不是“下载到 NAS 完成”。这一状态语义不能直接用于本项目。

结论：该仓库不足以提供其公网服务的完整搜索与转存后端。第一版没有必要复制它的公众号登录、链接交付或转存归因流程，也不应依赖其服务来完成本地程序的核心功能。

## 9. 全新程序需要自己建设的部分

推荐的内部结构如下；这是能力划分，不是本次已经写出的代码：

```text
统一界面 / 本机 API
  ├─ SearchEngine：来源调度、解析、去重、流式结果
  ├─ ShareResolver：分享规范化、目录预览、可选文件
  ├─ QuarkProvider：账号、转存、转存结果、原文件直链
  ├─ DownloadEngine：Range、并发、分片记录、恢复、校验
  ├─ TaskEngine：阶段编排、重试、取消、持久化
  └─ NASStorage：授权根目录、文件冲突、临时文件、完成改名
```

完整链路是“搜索源获得分享 → 用户选资源和 NAS 目录 → 读取分享清单 → 转存到自己的夸克 → 确认转存后的文件 ID → 获取原文件直链与匹配的请求头 → 本程序分片下载到临时文件 → 验证 → 完成落盘”。不经过 AList 或 PanSou 的本地服务接口。

需要新建而非简单提取的关键能力：

- 任务与文件逐项持久化，程序重启后能区分待转存、已转存和下载中的任务。
- 转存请求超时后的结果核对，避免重复转存产生副本。
- 分片完成记录与真实写入数据的一致性，避免预分配文件的大小被误认为下载完成。
- 校验 `206` 与 `Content-Range`；上游忽略 Range 返回 `200` 时安全降级，而不是把完整响应写入错误偏移。
- 下载直链过期后重新取链，并核对文件身份，避免不同文件版本拼接；更新下载会话时保持请求头一致。
- 全局和单文件并发限额、限流退避、暂停和取消；不能用上游临时重试替代持久化断点恢复。
- 授权 NAS 根目录与不可信文件名处理，阻止路径穿越、符号链接越界和静默覆盖。
- 临时文件完成后再进入正式目录/正式名称；存在可信哈希时校验哈希，只有大小时明确校验能力。

## 10. 优先验证顺序

第一步验证夸克下载能力：在相同 NAS、账号、原始文件和相近网络条件下，对照用户现有 AList 复制与最小直链下载实验，分别测试单连接和保守并发，记录吞吐、失败、内存与落盘结果。用于确认提取目标是否确实复现用户看重的性能；当前未进行该实验。

第二步验证分享转存：带提取码分享、嵌套目录、批量文件、转存后 FID、超时恢复和重复操作。只检查转存接口返回成功不足以通过。

第三步验证少量搜索源：实际搜索与详情页解析、结果链接和提取码、普通网络可达性。选择适合 NAS 环境的来源后，再扩大来源数量。

第四步整合新程序的任务、界面与 FPK。最终验收必须使用真实 fnOS 安装和真实文件下载；源码调研或模拟接口不能替代设备验收。
